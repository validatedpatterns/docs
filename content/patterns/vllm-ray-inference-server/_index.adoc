= About the {vllm-ray-pattern}

The {vllm-ray-pattern} deploys a private, OpenAI-compatible large language model (LLM) endpoint on {rh-ocp}. {rh-gitops} deploys every component from your fork of the pattern repository, and the cluster builds the server image itself from upstream packages. Eugo maintains the pattern as community content in the {sandbox-tier-first}.

[WARNING]
====
On {AWS}, the default installation creates one billable GPU instance: a `g6.2xlarge` instance with one NVIDIA L4 GPU. AWS bills the instance for as long as it runs. To skip the instance, set `global.gpuMachineSet: none` in the `values-global.yaml` file in your fork, and push the change before you install the pattern. On other platforms, the pattern creates no instance. Uninstalling the pattern does not delete the instance. For the steps to delete it, see link:getting-started/#uninstalling-the-vllm-ray-pattern[Uninstalling the pattern].
====

[id="background-vllm-ray"]
== Background

The {vllm-ray-pattern} complements the Red{nbsp}Hat AI products, such as {rhoai}. The pattern is a small, community-maintained reference point: the upstream vLLM engine on Ray Serve, built from known versions and measured the same way each time. The pattern does not need a {rhoai} subscription.

Your fork of the pattern repository describes the whole deployment: GPU enablement, the server, a model cache, a secret for gated models, and a timing notebook. You run the `./pattern.sh make install` command one time. After that, {rh-gitops} syncs each commit on your branch. It does not delete the objects that a commit removes, and it does not change the image of the running server or notebook. A job in the cluster starts new image builds: every 10 minutes, it starts a build when the server or notebook folder changed and no build of that image is running. For details, see link:https://github.com/eugo-inc/vllm-ray-inference-server/blob/main/AGENTS.md#updating-a-running-install[Updating a running install] in the pattern repository.

The pattern pins every Python package by hash and installs wheels only. It pins the base images of the server and the notebook by digest, and the default model by its Hugging Face commit. Some parts are not pinned, among them the system packages that the server image installs with `dnf`, the Operator versions, and the patch versions of the Validated Patterns Helm charts. Two builds from the same commit therefore install the same Python packages, but their system packages can differ.

The notebook measures the server in your cluster: the time from pod start to `Ready`, the time to first token, the decode speed of one stream, and the token throughput at 1, 8, and 32 concurrent requests. The notebook chooses its prompts from a fixed seed, and every request uses a temperature of 0 and a fixed number of output tokens. The time to `Ready` is in whole seconds and can trail the server by up to about 2 seconds.

The server runs Ray Serve LLM and the vLLM engine in one pod of a standard deployment, without KServe or KubeRay. Ray, vLLM, and PyTorch come from PyPI and run on the NVIDIA CUDA image that is based on Red{nbsp}Hat Universal Base Image 9. The pattern creates no KServe `InferenceService` or `ServingRuntime` resource.

By default, the pattern installs the {rh-nfd} and the NVIDIA GPU Operator itself, and on a cluster that already runs these Operators, the pattern can conflict with them. On such a cluster, set `global.gpuOperators: reuse` before you install: the pattern then uses the cluster's own Operators and does not change them. For what the cluster's Operators must provide, see link:https://github.com/eugo-inc/vllm-ray-inference-server#reuse-the-clusters-gpu-operators[Reuse the cluster's GPU operators] in the pattern README. The reuse setting has run on one test cluster so far. The pattern has not been tested on a cluster that runs {rhoai}.

== Architecture

.Architecture of the {vllm-ray-pattern}
image::/images/vllm-ray-inference-server/architecture.svg[Diagram of the vLLM Ray Inference Server pattern. The Validated Patterns Operator and OpenShift GitOps deploy secrets management, GPU enablement, the inference server, and the notebook from your Git fork.]

The pattern works in the following way:

* The {validated-patterns-op} installs {rh-gitops} and points the Argo CD instance at your fork. The `clustergroup` Helm chart then creates every application that the `prod` variant lists.
* {hashicorp-vault} and the {eso-op} deliver an optional Hugging Face token to the server as a Kubernetes secret. The default model is not gated and needs no token.
* The {rh-nfd} and the NVIDIA GPU Operator prepare the GPU node. On AWS, an imperative job creates the GPU node.
* A `BuildConfig` object builds the server image inside the cluster. The server deployment runs one pod with a Ray head, Ray Serve, and the vLLM engine on one GPU. The pod reports `Ready` only after the model loads.
* A persistent volume claim keeps the model weights across pod restarts.
* A JupyterLab notebook runs behind the OpenShift OAuth proxy. Only users who can edit the `vllm-notebook` namespace can open it. The notebook sends requests to the server through the in-cluster service.

[id="components-vllm-ray"]
== Components that the pattern deploys

The pattern deploys the following Operators:

* {rh-gitops}
* The {validated-patterns-op}, a community Operator
* The {eso-op} for Red{nbsp}Hat OpenShift
* The {rh-nfd}, by default. With `global.gpuOperators: reuse`, the pattern uses the cluster's own instead.
* The NVIDIA GPU Operator, from the certified Operators catalog, by default. With `global.gpuOperators: reuse`, the pattern uses the cluster's own instead.

The pattern deploys the following applications:

* {hashicorp-vault}, from the {solution-name-upstream} Helm chart.
* The inference server. Ray Serve LLM runs the vLLM engine and serves an OpenAI-compatible API on port 8000. The default model is `Qwen/Qwen2.5-0.5B-Instruct`. The server image turns off the usage statistics of Ray and vLLM.
* The notebook. A JupyterLab notebook measures the running server: the time from pod start to `Ready`, the time to first token, the decode speed of one stream, and the token throughput at several concurrency levels.

The link:https://github.com/eugo-inc/vllm-ray-inference-server#what-is-in-the-stock-stack[pattern README] lists the exact version of each component.

[id="compare-scale-out-vllm-ray"]
== Image comparison and scale out

The pattern has two optional features, and both are off by default:

* *Image comparison.* A job in the cluster runs two server images through the same benchmark, on the same GPU, with the same model and requests. The job records the time to ready, the time to first answer, and, at each load level, the time to first token, the inter-token latency, the output tokens per second, and the output tokens per joule of GPU energy. Each round also starts an identical copy of each image. A rule that is fixed before the first launch counts a difference between the images only when it is larger than the gap between two starts of one image and significant in an exact sign test over the paired rounds. The sign test, Holm's correction, and the calculation of the fewest rounds that a verdict needs come from link:https://github.com/eugo-inc/pairbench[pairbench] 0.1.0, an open source Python package from Eugo that the pattern installs unmodified from PyPI with pinned hashes. Each case ends with a verdict, such as FASTER, SLOWER, or TIE, or with NO VERDICT and a reason. A run scales the inference server to zero pods for its whole length.
* *Scale out.* Ray Serve can add vLLM replicas inside the server pod. With `global.scaleOut.mode: keda`, the Red{nbsp}Hat Custom Metrics Autoscaler, the supported build of KEDA, adds whole server pods when the vLLM count of waiting requests per pod rises above a set limit, and removes them after a cooldown. The image comparison also has a scale-out mode: at a fixed request rate, it starts a second replica of each image at a fixed time, and measures how soon that replica gives its first answer and what share of the requests meets the latency goals. This mode runs either with Docker on one machine or as the job in the cluster.

On {ocp}, the image comparison has had one full-length run with the default settings, and both autoscalers only short test runs, on new clusters on AWS, each with one NVIDIA L4 GPU. The full-length run compared upstream vLLM 0.33.0 with the pattern's own server (vLLM 0.29.0 on Ray Serve LLM) and gave verdicts on all 4 of its primary cases. Upstream vLLM 0.33.0 came out ahead in all 4. The two sides differ in both vLLM version and serving stack, so the run does not say which of the two made the difference. That run's cluster already ran the {rh-nfd} and the NVIDIA GPU Operator, and the pattern reused them through the `global.gpuOperators: reuse` setting, which is now on the pattern's `main` branch. Shorter comparisons, also in the scale-out mode, finished every launch, and each autoscaler added a second vLLM replica or pod under load. For the settings, the steps, and what has not been checked, see the link:https://github.com/eugo-inc/vllm-ray-inference-server#compare-two-images[Compare two images] and link:https://github.com/eugo-inc/vllm-ray-inference-server#scale-out[Scale out] sections of the pattern README.

== Partner results: Eugo

Eugo measured its next release build against the upstream `vllm/vllm-openai` v0.33.0 image, with Qwen2.5-0.5B-Instruct on one NVIDIA DGX Spark shared with other jobs, in Docker containers, not on {ocp}. The Eugo build runs a vLLM development snapshot taken after 0.33.0 branched off, plus Eugo's fixes. Every start was a new container with empty compile caches, with the model files already in memory and the image already on the machine. Both sides got the same settings apart from the attention setting that the table names. Some of those settings were not the defaults. Every run in the table gave vLLM 12% of GPU memory (vLLM's default is 92%, this pattern's 85%), because the NVIDIA DGX Spark's GPU shares its memory with the CPU and with those other jobs. In the rows that name `--safetensors-load-strategy eager`, both sides used it in place of vLLM's default weight loading. Each lead is the median of the differences over paired rounds.

In the tuned runs, the vLLM start-up memory check stopped 2 of 36 upstream first tries and none of 12 Eugo first tries, too few to show a difference by Fisher's exact test. In the run with only the 12% GPU memory setting, every upstream and Eugo start succeeded on its first try (12 of 12 starts each).

Against upstream as shipped, the time per output token was a tie, at one stream through this pattern's server, in a short check. Most of that time is set by the hardware: at one stream, each output token needs all of the model's weights, about 0.99 GB, read from memory, which at the NVIDIA DGX Spark's published memory bandwidth of 273 GB/s takes at least 3.6 ms of the measured 5.8 ms per token for both servers. The rest depends on the software and on how much of that bandwidth the GPU reaches; in this check both servers used FlashAttention-2 for attention.
